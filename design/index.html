Materin UI v0.1

一套 UI，三个插件，一个网页 —— 颜色、形状、间距、命名都从一个文件里取。 One UI for three plugins and one site — colour, shape, spacing and naming all come from a single file.

令牌文件Token file ↘ 组件清单Component registry ↘ 校验脚本Checker ↘

三条原则

颜色跟随，形状固定

颜色取宿主的主题变量：在 Obsidian 里换成任何主题，插件跟着变，不需要改代码；在网页里没有宿主变量，就用品牌默认值。圆角和间距反过来固定下来，谁都不许即兴发挥。

只有一个改风格的地方

界面代码里不允许出现裸色值（#1f1f1f 这种），一律引用 --materin-*。改一个文件，三个插件和本站一起变。

组件按名定位

每个组件有唯一的、带用途的名字，并登记在组件清单里。人和 AI 都能按名找到它、按名改它，改样式时不会改错地方、也不会漏。

取值规则是「先宿主、后品牌」：表中列出的是宿主变量缺失时的回落值。下面的色块直接引用令牌，所以你看到的就是当前主题下的真实取值。

组件命名契约

界面要能被「按名查找、按名维护」，前提是名字本身就是说明书。所以只允许这几种前缀：

类型模式例子
组件materin-<scope>-<component>[__part][--variant]materin-site-card / materin-site-card__meta / materin-site-btn--primary
布局 / 工具materin-u-<name>materin-u-wrap / materin-u-grid / materin-u-mono
状态is-<state>，或优先用 ARIA 属性materin-site-chip[aria-pressed="true"] / .is-active

scope 只有五个：ui（共享件）、site（本站 UI）、office、view、ctx。名字里必须带 scope，这样在全仓库范围搜 materin-ctx- 就能一次拿到该插件的全部 UI。

不用裸类名（.card、.btn 这种），也不做「换个前缀的别名」—— 一个组件只有一个名字，否则按名查找会落空。i18n 的 lang-zh / lang-en 是系统约定，不属于组件，不参与改名。

清单与守门

每个组件登记在 组件清单：名字、范围、用途、部件、变体、状态、所在文件。清单不是文档，是给工具读的 —— 校验脚本提交前跑一遍，五项检查：

  • 契约：所有类名符合上面的模式（裸类名直接报错）
  • 存在：用到的组件必须在 CSS 里有定义
  • 注册：CSS 里定义的组件必须登记进清单
  • 反向：清单里的名字必须真的存在（防止改完名字忘了改清单）
  • 令牌：组件层不得出现裸色值

当前结果：33 条组件注册、49 个选择器、48 个类名，全部通过。这就是「按名维护」能成立的原因 —— 名字和实现不允许对不上。

透明与半透明

视觉按 macOS 一贯的透明语言做：界面分层，靠背景模糊和描边把层次交代清楚，而不是靠纯色块堆叠。分四层：

  • 底色：不透明，负责整体明暗
  • 玻璃面：74%（顶栏）／66%（卡片）透明 + 背景模糊，让下层内容透出一点
  • 高光边：卡片左上到右下的一层白 12% 斜向渐变，加正视作「面」而不是「洞」
  • 阴影：半透明面必须配阴影，否则浮不起来；悬停时阴影升一级并抬升 3px

透明度不是越低越好看。文字要读得清，所以实测了对比度：

主题卡片正文卡片标题顶栏导航
深色7.13 : 115.65 : 17.36 : 1
浅色5.51 : 117.12 : 15.29 : 1

全部高于无障碍标准要求的 4.5 : 1。做法是「玻璃底 + 实色文字」：文字永远用 --materin-text，不给文字加透明度 —— 那是最容易把可读性做没的一步。

降级

  • 宿主不支持 backdrop-filter（老内核）：令牌自动换成不透明表面，布局、文字、层级不变
  • 用户系统开了「减少透明度」（prefers-reduced-transparency: reduce）：同上，自动退回不透明
  • 两种降级都只改令牌值，组件层不需要写任何一条额外规则 —— 这也是把透明度做成令牌的原因

怎么用

网页：在站点自己的样式之前引入令牌表 ——

<link rel="stylesheet" href="/assets/css/materin-ui.css">
<link rel="stylesheet" href="/assets/css/style.css">

插件：把令牌文件里的 :root 段复制到插件 styles.css 顶部。不做运行时远程 @import：Obsidian 插件打包成单文件，而且要能离线用，远程依赖只会变成新的故障点。

之后新增 UI：只用 --materin-*；组件按契约命名并登记进清单；提交前跑一次校验脚本。三条都做到，三个插件就不会再各自漂移。

Three principles

Colours follow, shape is fixed

Colours come from the host theme: switch themes in Obsidian and the plugins follow, with no code change; on the web there is no host variable, so brand defaults apply. Radius and spacing go the other way — fixed, no improvising.

One place to restyle

No raw colour values in UI code (#1f1f1f and friends) — everything references --materin-*. Change one file and all three plugins plus this site change with it.

Components you can find by name

Every component has a unique, purpose-bearing name and an entry in the registry. People and AI can both locate it and change it by name — without touching the wrong rule or missing one.

Tokens

The rule is host-first, brand-second: the value listed is the fallback used when the host variable is absent. The swatches below reference the tokens directly, so what you see is the real value in the current theme.

Component naming contract

UI that can be found and maintained by name needs names that document themselves. Only these prefixes are allowed:

KindPatternExamples
Componentmaterin-<scope>-<component>[__part][--variant]materin-site-card / materin-site-card__meta / materin-site-btn--primary
Layout / utilitymaterin-u-<name>materin-u-wrap / materin-u-grid / materin-u-mono
Stateis-<state>, ARIA attributes preferredmaterin-site-chip[aria-pressed="true"] / .is-active

There are five scopes: ui (shared), site (this site), office, view, ctx. The scope is mandatory, so grepping materin-ctx- across the repos returns that plugin's entire UI in one go.

No bare class names (.card, .btn), and no prefixed aliases either — one component, one name, otherwise a lookup by name silently misses. The i18n pair lang-zh / lang-en is a system convention, not a component, and is exempt from renaming.

Registry and gatekeeper

Every component is registered in the component registry: name, scope, purpose, parts, variants, states, file. The registry is not documentation — it is read by tooling. The checker runs five checks before each commit:

  • Contract: every class name matches the pattern (bare names fail)
  • Existence: anything used must be defined in CSS
  • Registration: anything defined in CSS must be in the registry
  • Reverse: every registry name must actually exist (catches a half-finished rename)
  • Tokens: no raw colour values in the component layer

Current result: 33 registered components, 49 selectors, 48 class names — all passing. That is what makes maintenance by name credible: a name and its implementation are not allowed to drift apart.

Transparent and translucent

The visual follows the translucency language macOS has been building for years: interface layered with background blur and light edges, rather than stacked opaque blocks. Four layers:

  • Base: opaque, sets overall lightness
  • Glass surfaces: 74% (top bar) / 66% (cards) alpha plus background blur, so content below shows through slightly
  • Specular edge: a diagonal white-12% gradient on cards, so they read as a surface rather than a hole
  • Shadow: translucent surfaces need shadow or they never lift off; hover raises one level and translates 3px

Lower opacity is not automatically better — text has to stay readable, so contrast was measured:

ThemeCard bodyCard titleTop-bar nav
Dark7.13 : 115.65 : 17.36 : 1
Light5.51 : 117.12 : 15.29 : 1

All above the 4.5 : 1 accessibility floor. The trick is glass underneath, solid text on top: text always uses --materin-text and is never given transparency — that is the one step that quietly destroys readability.

Fallbacks

  • Host without backdrop-filter (older engine): tokens switch to opaque surfaces — layout, text and layering unchanged
  • System-level "Reduce transparency" (prefers-reduced-transparency: reduce): same, falls back to opaque
  • Both fallbacks only change token values; the component layer needs no extra rules — which is exactly why translucency was made a token

How to use it

On the web: link the token sheet before the site's own styles —

<link rel="stylesheet" href="/assets/css/materin-ui.css">
<link rel="stylesheet" href="/assets/css/style.css">

In a plugin: copy the :root block from the token file to the top of the plugin's styles.css. No runtime remote @import — Obsidian plugins ship as a single bundle and must work offline; a remote dependency would just be another failure mode.

For new UI: reference --materin-* only; name components per the contract and register them; run the checker before committing. Do those three and the plugins stop drifting apart.
